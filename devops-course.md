# 01. DevOps и Git

Зачем вообще конвейер поставки и как хранить изменения так, чтобы их можно было откатить.

К концу модуля: Заведёте репозиторий, ветку и пул-реквест, не положив туда пароль.

Уроков: 6. С зачётом около 3 ч 15 мин.

## 1.1. Чем DevOps отличается от ручной настройки

Около 25 мин. Один и тот же путь от коммита до работающего сервиса, который можно повторить.

**Теория**

DevOps — это способ выпускать изменения маленькими шагами и отвечать за то, что сервис жив. Сисадмин часто настраивает сервер руками и помнит, что он делал. Инженер поставки записывает те же шаги в файлы: образ, манифест, пайплайн. Тогда второй человек и завтрашний вы получаете тот же результат. Культура здесь короткая: изменение маленькое, оно проходит проверку, его можно откатить, за ним кто-то смотрит. Инструменты без этого превращаются в ещё один ручной ритуал. Этот курс идёт по стеку, который в 2026 году повторяют программы Яндекс Практикума, Нетологии и практические треки вроде KodeKloud: Git, контейнеры, Kubernetes, Terraform, Ansible, GitOps и метрики. Текст уроков свой, не конспект чужой школы.

**Практика. Один сервис на бумаге**

Описать путь учебного сайта от правки до адреса, которым его открывают.

1. Кто меняет код.
2. Где он собирается.
3. Куда выкладывается.
4. Как понять, что он умер.
5. Как откатиться.

Сделано, когда:

- Пять пунктов есть
- Откат назван
- Это не «зайти по SSH и поправить на сервере» как единственный путь

### Проверка

**1. Ручная правка только на боевом сервере**

- А. не повторяется и плохо откатывается ← верный ответ
- Б. лучший GitOps
- В. заменяет тесты
- Г. не оставляет следа никогда

Пояснение: Завтра никто не вспомнит, что вы поменяли.

## 1.2. Репозиторий и коммит

Около 30 мин. Git хранит снимки. Коммит — маленькое сообщение о одном изменении.

**Теория**

Репозиторий заводят локально командой git init или клонируют чужой через git clone. Файл меняют, git status показывает разницу, git add выбирает, что войдёт в снимок, git commit записывает его с сообщением. Сообщение говорит, зачем, а не «fix». git log листает историю. Не коммитьте папку node_modules, бинарный мусор и дампы: для этого есть .gitignore. Один коммит — одна мысль. Десять несвязанных правок в одном коммите потом не откатить выборочно.

**Практика. Три коммита**

Создать репозиторий с README и двумя осмысленными коммитами.

1. git init.
2. README.
3. Коммит.
4. Вторая маленькая правка и второй коммит.
5. git log.
6. Секретов в файлах нет.

Сделано, когда:

- Два коммита с понятными сообщениями
- status чистый
- Пароля в истории нет

### Проверка

**1. git commit без сообщения о сути**

- А. плохая история ← верный ответ
- Б. обязательный стиль
- В. быстрее ревью
- Г. так хранят пароли

Пояснение: Историю читают люди и вы сами через месяц.

## 1.3. Ветки и пул-реквест

Около 30 мин. main остаётся рабочим. Изменение живёт в ветке, пока его не посмотрели.

**Теория**

Ветка — указатель на цепочку коммитов. main или master не ломают напрямую, если в репозитории больше одного человека. Новую ветку создают от свежего main, коммитят туда и открывают пул-реквест или merge request: просьбу влить изменение. Ревьюер смотрит diff. Конфликт возникает, когда две ветки поправили одни строки: его решают, а не выбирают «взять всё моё» не читая. После вливания ветку удаляют. force push в main на общем репозитории запрещают правилами, не договорённостью в чате.

**Практика. Одна ветка**

Сделать ветку, коммит и пул-реквест в своём учебном репозитории на GitHub или локальный merge после просмотра diff.

1. git switch -c.
2. Маленькая правка.
3. Посмотреть diff.
4. Влить только после просмотра.
5. main по-прежнему собирается хотя бы как текст README.

Сделано, когда:

- Diff прочитан
- main не правили вслепую
- Чужой репозиторий не использован

### Проверка

**1. Прямые коммиты в main у команды**

- А. ломают всем базу, от которой ответвляются ← верный ответ
- Б. единственный профессиональный способ
- В. нужны для Docker
- Г. заменяют ревью

Пояснение: Общую ветку берегут.

## 1.4. Секреты не коммитят

Около 25 мин. Пароль в git остаётся в истории, даже если файл потом удалили.

**Теория**

Файл .env, ключ облака и kubeconfig — секреты. Их пишут в .gitignore до первого коммита. Если секрет уже попал в историю, смена файла в новом коммите его не стирает: история хранит старый блоб. Ключ считают скомпрометированным и перевыпускают. В репозитории лежит пример .env.example без значений. Настоящие значения приходят из переменных CI или менеджера секретов, не из чата. Проверка перед пушем: git status и поиск слова password в diff.

> Не выкладывайте ключи облака и приватные SSH-ключи.

**Практика. Игнор**

Добавить .env в gitignore и убедиться, что git status его не показывает как новый файл для коммита.

1. Создать .env с фейковым паролем.
2. Строка в .gitignore.
3. status не предлагает .env.
4. example-файл без значения закоммитить.
5. Если успели закоммитить секрет — не пушить, а выкинуть коммит, пока он только локальный.

Сделано, когда:

- Секрет вне индекса
- Пример без значения есть
- В удалённый репозиторий секрет не ушёл

### Проверка

**1. Удалить пароль следующим коммитом**

- А. не вычищает его из старой истории ← верный ответ
- Б. достаточно всегда
- В. шифрует прошлые коммиты
- Г. так устроен gitignore

Пояснение: История помнит файл.

## 1.5. YAML и JSON

Около 25 мин. Почти все инструменты курса говорят на YAML. Отступ пробелами, не табами.

**Теория**

YAML описывает пайплайны, манифесты Kubernetes и часть Ansible. Пробелы задают вложенность, таб часто ломает файл. Двоеточие с пробелом отделяет ключ от значения. Списки начинают с дефиса. JSON — тот же смысл скобками, его любят API. Число, строка и булево различаются: "yes" в старом YAML бывал ловушкой, в новых файлах пишите true и кавычки вокруг версий вроде "1.29", чтобы их не съели как число. Проверяют файл глазами и линтером, не выкладкой на прод.

**Практика. Один манифест-черновик**

Написать короткий YAML с вложенностью и списком и открыть его без ошибки парсером или хотя бы единообразными отступами.

1. Пробелы по два.
2. Список из двух шагов.
3. Строковая версия в кавычках.
4. Табов нет.
5. Секрета внутри нет.

Сделано, когда:

- Файл читается
- Отступы ровные
- Это ваш файл, не вставка неизвестного манифеста

### Проверка

**1. Таб в отступе YAML**

- А. частая причина тихой поломки ← верный ответ
- Б. рекомендуется
- В. нужен для Git
- Г. равен JSON

Пояснение: Инструменты ждут пробелы.

## 1.6. Удалённый репозиторий

Около 20 мин. origin — это GitHub, GitLab или другой хост. push отправляет ваши коммиты, pull забирает чужие.

**Теория**

git remote показывает, куда связан локальный репозиторий. git push -u origin ветка отправляет ветку. git pull забирает изменения и сливает их. Перед пушем в общую ветку делают pull. SSH-ключ или токен с ограниченными правами лучше пароля от всего аккаунта в настройках git. Токен — секрет, его не вшивают в URL, который попадёт в лог. Учебный репозиторий может быть приватным. Чужие учебные форки не переписывают.

**Практика. Пуш ветки**

Отправить свою ветку на хост, которым вы владеете.

1. Приватный репозиторий.
2. push ветки.
3. На сайте виден коммит.
4. Токен не в файле репозитория.
5. main защищён хотя бы вашей привычкой не пушить туда напрямую.

Сделано, когда:

- Коммит виден на сайте
- Секрет не в URL внутри файлов
- Это ваш репозиторий

### Проверка

**1. Токен доступа в URL внутри репозитория**

- А. утечёт при любом клоне ← верный ответ
- Б. так и надо
- В. это gitignore
- Г. шифруется сам

Пояснение: URL с токеном светится в конфиге и логах.

К концу модуля: Соберёте образ учебного веб-приложения и поднимете его вместе с зависимостью через Compose.

## 2.1. Образ и контейнер

Около 25 мин. Образ — шаблон слоёв. Контейнер — запущенный процесс с этим шаблоном.

**Теория**

Контейнер изолирует процесс: свои файлы, своя сеть, ограниченные права. Это не отдельная виртуальная машина с своим ядром. Образ собирают один раз и запускают где угодно, где есть совместимый Docker или другой runtime. Контейнер смертен: данные внутри него пропадают, если их не вынесли на том. Поэтому базу не держат только внутри контейнера без тома. Официальный Docker Engine или Docker Desktop ставят с сайта разработчика. Чужой «Docker с кряком» не нужен: сам движок бесплатен для учёбы.

**Практика. hello**

Запустить официальный образ hello-world или короткий nginx и остановить контейнер.

1. Движок с официального источника.
2. docker run.
3. docker ps и docker ps -a.
4. Остановить контейнер.
5. Не публиковать порт в интернет на роутере.

Сделано, когда:

- Контейнер стартовал
- Остановлен
- Проброса наружу нет

### Проверка

**1. Контейнер — это**

- А. процесс из образа, не отдельный компьютер с своим ядром ← верный ответ
- Б. всегда виртуалка
- В. файл git
- Г. кластер Kubernetes

Пояснение: Ядро общее с хостом.

## 2.2. Dockerfile

Около 35 мин. Инструкция сборки. Маленький базовый образ и непривилегированный пользователь.

**Теория**

Dockerfile начинается с FROM. COPY кладёт файлы, RUN выполняет команду во время сборки, CMD задаёт процесс при старте. Каждый шаг — слой, и слои кешируются: то, что меняется часто, пишут ниже, чтобы не пересобирать зависимости зря. Базовый образ берут официальный и по возможности маленький. В конце заводят обычного пользователя и не оставляют процесс root без причины. Секреты не передают через ARG, который останется в истории слоёв. .dockerignore убирает .git и .env из контекста сборки.

**Практика. Свой образ**

Собрать образ, который отдаёт одну страницу или печатает строку.

1. Dockerfile.
2. .dockerignore.
3. docker build.
4. docker run локально.
5. В образе нет .env.

Сделано, когда:

- Образ собрался
- Процесс не обязан быть root
- Секрет не в контексте

### Проверка

**1. Секрет в ARG Dockerfile**

- А. может остаться в слоях ← верный ответ
- Б. автоматически скрыт
- В. так рекомендует реестр
- Г. равен .dockerignore

Пояснение: Слои читаются.

## 2.3. Тег и реестр

Около 25 мин. Тег latest плавает. Для выкладки нужен неизменяемый тег или дайджест.

**Теория**

Образ именуют реестр/имя:тег. latest каждый день может указывать на другое содержимое, поэтому пайплайн выкладки по latest непредсказуем. Учебный тег делают по короткому хешу коммита. Реестр — Docker Hub, GitHub Container Registry или реестр в вашей сети. Публичный образ сначала смотрят: кто издатель. Приватный реестр требует входа, пароль от него не в Dockerfile. Локально docker images показывает, что уже скачано. Чужие образы «со всеми тулзами и майнером» не запускают.

**Практика. Тег коммита**

Пометить свой образ тегом, который не называется latest, и записать, куда вы его положите.

1. Тег с хешем или датой.
2. Не пушить секрет.
3. Если реестра нет — образ остаётся локальным, это нормально.
4. Издатель базового образа официальный.

Сделано, когда:

- Тег не latest
- База официальная
- Пароль реестра не в git

### Проверка

**1. Выкладка всегда с тегом latest**

- А. непредсказуема ← верный ответ
- Б. лучший GitOps
- В. фиксирует дайджест
- Г. нужна для томов

Пояснение: Тег переезжает на новый образ.

## 2.4. Тома и сеть

Около 25 мин. Данные живут на томе. Контейнеры одной сети видят друг друга по имени.

**Теория**

Том Docker переживает удаление контейнера. База пишет в том, а не в слой контейнера. Бинд-маунт каталога с хоста удобен в разработке и опасен, если смонтировать корень хоста или сокет Docker внутрь контейнера: процесс внутри получит власть над хостом. Сеть bridge даёт контейнерам имена. Публикация порта -p 8080:80 доступна на вашем компьютере. На роутере этот порт наружу не открывают. Два контейнера не обязаны делить сеть хоста.

> Не монтируйте сокет Docker и корень диска в контейнер.

**Практика. Том**

Запустить контейнер с томом, записать файл и увидеть его после пересоздания контейнера.

1. Именованный том.
2. Файл внутри.
3. Контейнер удалить.
4. Новый контейнер с тем же томом видит файл.
5. Корень хоста не смонтирован.

Сделано, когда:

- Файл пережил контейнер
- Порт только локальный
- Сокет Docker не отдан внутрь

### Проверка

**1. Сокет Docker, смонтированный в контейнер**

- А. даёт контроль над хостом ← верный ответ
- Б. нужен для учебного nginx
- В. это том базы
- Г. безопасен всегда

Пояснение: Кто говорит с сокетом, тот запускает контейнеры на хосте.

## 2.5. Docker Compose

Около 30 мин. Несколько контейнеров в одном файле: приложение и база, общие сеть и тома.

**Теория**

Compose описывает сервисы, образы, порты, тома и переменные. Файл compose.yaml лежит в git, значения секретов приходят из окружения, не из файла с паролем. docker compose up поднимает всё, down останавливает. Для учёбы хватит приложения и базы на внутренней сети Compose, порт наружу только у приложения на localhost. Зависимость базы от готовности проверяют healthcheck, а не sleep 30 как единственный способ. Это ещё не Kubernetes: Compose хорош на одной машине.

**Практика. Два сервиса**

Поднять приложение и второй контейнер в одной сети Compose.

1. compose.yaml в git.
2. Секрет через переменную, не в файле коммита.
3. up.
4. Сервисы видят друг друга по имени.

Сделано, когда:

### Проверка

## 2.6. Логи и перезапуск

Образ, который не стартует локально, не отправляют в кластер.

# 03. Непрерывная интеграция

GitHub Actions как доступный конвейер. GitLab CI и Jenkins устроены похоже, их узнаете по тем же шагам.

К концу модуля: На каждый пуш прогоните тест и сборку образа, не деплоя сломанный коммит.

Уроков: 6. С зачётом около 3 ч 10 мин.

## 3.1. Зачем пайплайн

Около 20 мин. Машина проверяет коммит раньше, чем человек выложит его руками.

**Теория**

Непрерывная интеграция значит: каждое изменение само проходит сборку и тесты. Если тест красный, изменение не вливают. Это дешевле, чем ловить ту же ошибку на сервере ночью. Пайплайн — файл в репозитории, не скрипт, который живёт только на ноутбуке одного человека. GitHub Actions, GitLab CI и Jenkins отличаются синтаксисом, но шаги одни: взять код, поставить зависимости, проверить, собрать артефакт. В 2026 году для учёбы удобнее Actions: бесплатный лимит на публичный или свой маленький репозиторий. Jenkins ещё часто стоит в компаниях, его не нужно учить первым, чтобы понять идею.

**Практика. Шаги на бумаге**

Выписать шаги пайплайна учебного приложения до любого YAML.

1. Checkout.
2. Тест.
3. Сборка образа.
4. Что считается провалом.
5. Деплой в этот список пока не входит.

Сделано, когда:

- Порядок записан
- Провал блокирует вливание
- Деплой не смешан с первой проверкой

### Проверка

**1. Красный тест**

- А. не вливают ← верный ответ
- Б. вливают и чинят на сервере
- В. это предупреждение без последствий
- Г. лечится тегом latest

Пояснение: Интеграция как раз про этот стоп.

## 3.2. Первый workflow GitHub Actions

Около 35 мин. Файл в .github/workflows запускается на push и на pull request.

**Теория**

Workflow — YAML. on выбирает событие. jobs содержит задачи на runner, виртуальной машине GitHub или своей. steps идут по порядку. actions/checkout забирает код. Команда теста — та же, что вы запускаете локально. Логи шага читают при падении, а не перезапускают вслепую десять раз. Секреты кладут в настройки репозитория, в YAML их вызывают по имени. Форк чужого репозитория не должен получать ваши секреты на pull request извне: это известная ловушка, учебный репозиторий держат своим.

> Не печатайте секреты в лог командой echo.

**Практика. Зелёный прогон**

Добавить workflow, который на push запускает хотя бы одну успешную команду проверки.

1. Файл workflow в git.
2. Событие push.
3. Шаг проверки.
4. Лог зелёный.
5. Секрет не выведен.

Сделано, когда:

- Прогон зелёный
- Файл в репозитории
- Лог без секретов

### Проверка

**1. echo секрет в логе Actions**

- А. светит его в истории прогона ← верный ответ
- Б. скрывает автоматически всегда
- В. так отлаживают прод
- Г. это gitignore

Пояснение: Логи читают многие.

## 3.3. Тест до сборки образа

Около 25 мин. Сначала дешёвая проверка, потом долгая сборка.

**Теория**

Порядок экономит минуты: линтер и юнит-тест быстрее сборки образа и тем более выкладки. Упавший тест останавливает следующие шаги. Тест должен уметь провалиться: один раз сломайте ожидание нарочно и убедитесь, что пайплайн красный, потом верните. Тест, который всегда зелёный, не проверяет ничего. Для учебного приложения хватит проверки, что страница или функция отдаёт ожидаемую строку. Базу в юнит-тесте не поднимают целиком, если можно обойтись без неё.

**Практика. Красный и снова зелёный**

Увидеть падение пайплайна и починку.

1. Рабочий тест.
2. Намеренная ошибка.
3. Красный прогон.
4. Исправление.
5. Зелёный прогон.

Сделано, когда:

- Был красный лог
- Стал зелёный
- Ошибка не осталась в main

### Проверка

**1. Тест, который нельзя уронить**

- А. бесполезен ← верный ответ
- Б. идеал
- В. заменяет ревью
- Г. нужен для Docker

Пояснение: Проверка обязана уметь сказать нет.

## 3.4. Сборка образа в пайплайне

Около 30 мин. Образ тегируют хешем коммита. Пароль реестра берётся из секрета.

**Теория**

После зелёных тестов пайплайн собирает образ и, если есть реестр, пушит его. Тег — github.sha или аналог, не latest. Логин в реестр идёт через секрет. На учебном контуре можно остановиться на локальной сборке в пайплайне без пуша, если реестра нет: важен сам шаг. Кеш слоёв ускоряет повтор. В образ не копируют каталог .git целиком без нужды. Пайплайн, который пушит latest поверх и сразу деплоит, вы научитесь не писать.

**Практика. Тег коммита**

Добавить шаг сборки с тегом, привязанным к коммиту.

1. Сборка после тестов.
2. Тег не latest.
3. Секрет реестра из настроек, если пушите.
4. Лог без пароля.
5. Сломанный тест до сборки не доходит.

Сделано, когда:

- Образ собирается в CI
- Тег уникальный
- Секрет не в YAML открытым текстом

### Проверка

- В. равен latest
- Г. кладёт пароль в слой

Пояснение: Хеш находит ровно тот образ.

## 3.5. Тот же конвейер в GitLab CI и Jenkins

Около 20 мин. Другой файл, те же этапы. Не учите три системы с нуля параллельно.

В GitLab файл .gitlab-ci.yml описывает stages: test, build, deploy. Runner может быть общим или вашим. В Jenkins пайплайн часто Jenkinsfile, агенты и плагины. Тащить Jenkins на свой ноутбук ради галочки в 2026 году необязательно, если вы уже собрали рабочий Actions. В вакансиях России GitLab CI встречается очень часто, синтаксис стоит прочитать один вечер на своём примере.

**Практика. Словарь**

## 3.6. Что гонять на пул-реквесте

Около 20 мин. На запросе вливания гоняют тесты. Выкладку в прод с непроверенной ветки не делают.

- Правило записано

# 04. Чужой конфиг веб-сервера

Как читать nginx, Apache и балансировщик, не выучив наизусть каждую директиву. Один и тот же разбор: кто слушает, какое имя, какой путь, куда уходит запрос и где журнал.

К концу модуля: По чужому файлу говорите, куда попадёт конкретный адрес, и замечаете опасную строку до правки.

Уроков: 6. С зачётом около 3 ч 45 мин.

## 4.1. Пять вопросов к любому файлу

Около 25 мин. Беглость — это один и тот же проход по файлу, а не память на все ключи nginx и Apache.

**Теория**

Конфиг веб-сервера пугает объёмом, пока его читают сверху вниз как прозу. Рабочий проход другой. На любой файл, свой или чужой, отвечают пять вопросов. Кто слушает: адрес и порт. Какое имя сайта выбирает этот блок. Какой путь запроса попадает в какое правило. Куда уходят байты: файл на диске или другой процесс. Где журнал и что будет, если следующий процесс молчит. Эти пять вопросов одинаковы для nginx, Apache и облачного балансировщика. Меняются только слова.

Чужой файл сначала копируют и читают. На боевой машине его не правят, пока карта не записана. Проверка синтаксиса, nginx -t или apachectl configtest, ловит опечатку и не отвечает, правильная ли схема. Включённый файл часто не тот, что открыли: nginx собирает куски через include, Apache держит живой сайт в sites-enabled. Полный текст смотрят командой, которая печатает уже собранный конфиг, а не один красивый кусок из документации.

Ниже учебный фрагмент. Его и разбирают в лаборатории. Он слушает только этот компьютер.

```
server {
  listen 127.0.0.1:8080;
  server_name lab.local;
  location / {
    root /var/www/lab;
  }
  location /api/ {
    proxy_pass http://127.0.0.1:9000;
  }
}
```

**Практика. Карта фрагмента**

Ответить на пять вопросов по фрагменту из теории, не меняя ни одного сервера.

1. Кто слушает: адрес и порт.
2. Какое имя.
3. Куда пойдёт запрос к / и к /api/health.
4. Где был бы журнал, если строка лога есть, и что её нет.
5. Что случится с /api/, если процесс на порту 9000 не запущен.

Сделано, когда:

- Пять ответов записаны
- Порт назван точно
- Боевой конфиг не трогали

### Проверка

**1. Проверка nginx -t**

- А. ловит синтаксис, не смысл схемы ← верный ответ
- Б. доказывает, что сайт правильно устроен
- В. заменяет чтение
- Г. открывает порт в интернет

Пояснение: Файл может быть верным по запятым и вредным по смыслу.

## 4.2. Как сложен nginx

Около 35 мин. Запрос выбирает один server и одну location. Побеждает самое конкретное правило, не верхняя строка файла.

**Теория**

Снаружи nginx — один процесс, который принимает соединение и решает, кому отдать запрос. Внутри файл вложен: http, внутри server, внутри location. server — это один сайт: адрес, порт и имя. location — кусок пути.

Имя берут из заголовка Host. Если имя не совпало ни с одним server_name, ответит блок с пометкой default_server, а если пометки нет — тот, который nginx считает умолчанием на этом порту. Поэтому чужой «лишний» server вдруг отвечает на ваш домен: смотрят, кто default.

Путь выбирают так. location = /health совпадает только с этим путём целиком. Обычный location /api/ — префикс, и более длинный префикс побеждает короткий: /api/v2/ точнее, чем /api/, если запрос туда. Регулярные location с тильдой — отдельная очередь. При чтении не начинают с них. Сначала выписывают точные и префиксные правила и пальцем ведут один конкретный URL.

Живой конфиг часто размазан по include. Команда nginx -T печатает уже собранный текст. Читают его, а не единственный файл, который попался в редакторе. Учебный сервер слушает 127.0.0.1. Строку listen 80 без адреса на машине, которая смотрит в интернет, не ставят, пока нет отдельного решения, кому этот порт нужен.

```
server {
  listen 127.0.0.1:8080 default_server;
  server_name lab.local;
  location / { root /usr/share/nginx/html; }
  location = /health { return 200 "ok"; }
  location /api/ { proxy_pass http://127.0.0.1:9000; }
}
```

> Слушайте 127.0.0.1. Порт наружу на роутере не открывают.

**Практика. Три адреса на своём nginx**

Поднять официальный образ nginx только на localhost и увидеть, что /health и / отвечают по-разному.

1. Образ nginx с конкретным тегом, порт опубликован как 127.0.0.1:8080, не 0.0.0.0 в интернет.
2. Свой файл с location / и location = /health.
3. curl на оба пути.
4. Записать, какой location ответил и почему.
5. nginx -t или лог контейнера, если файл не принялся.

Сделано, когда:

- Оба ответа разные и ожидаемые
- Слушает только localhost
- Причина выбора location записана

### Проверка

**1. Запрос /api/v2/users при наличии location / и location /api/**

- А. ближе префикс /api/ ← верный ответ
- Б. всегда самый верхний location
- В. всегда регулярное выражение
- Г. имя server_name

Пояснение: Более длинный подходящий префикс конкретнее.

## 4.3. Прокси: запрос уходит дальше

Около 30 мин. proxy_pass отдаёт запрос другому процессу. 502 значит, что nginx жив, а тот процесс нет.

**Теория**

Если location отдаёт root, nginx сам читает файл. Если стоит proxy_pass, nginx становится клиентом следующего сервиса: приложения, Apache, другого nginx. В чужом файле это главная стрелка. Её выписывают: путь снаружи → адрес внутри.

Косая черта в конце proxy_pass меняет путь. proxy_pass http://app:9000/api/ и proxy_pass http://app:9000 — не одно и то же: в одном случае кусок URL подменяют, в другом передают как пришёл. Это частая причина «у меня 404, хотя приложение живое». Сверяют путь в журнале приложения, не только ответ браузера.

502 и 504 при живой странице nginx значат: следующий процесс не принял соединение или не успел. 404 может нарисовать и nginx, и приложение. curl -sv к своему localhost показывает, кто ответил и какой заголовок пришёл. Заголовок Host приложение иногда проверяет. Если nginx его не передаёт, приложение отвечает чужим сайтом или отказом. В чужом конфиге ищут proxy_set_header Host.

Открытый прокси — это когда nginx пересылает запрос на любой адрес, который подставил клиент. Учебный proxy_pass указывает на ваш фиксированный процесс, не на адрес из запроса. Так файл и читают: стрелка должна заканчиваться на известном вам сервисе.

> Не делайте proxy_pass на адрес, который прислал клиент. Это открытый прокси.

**Практика. 502 своими руками**

Направить /api/ на порт, где никого нет, увидеть 502, затем поднять свой ответ и увидеть 200.

1. location /api/ с proxy_pass на 127.0.0.1 и свободный порт.
2. curl и код 502.
3. Поднять на этом порту простой ответ только на localhost.
4. Тот же curl и успех.
5. Записать одной фразой, чем 502 отличается от «nginx не запущен».

Сделано, когда:

- Был 502
- Стал успешный ответ
- Стрелка в конфиге на свой порт

### Проверка

**1. 502 от nginx**

- А. nginx работает, следующий сервис не ответил ← верный ответ
- Б. nginx не установлен
- В. так выглядит успешный прокси
- Г. это ошибка DNS имени lab.local всегда

Пояснение: Страница ошибки nginx как раз признак, что он жив.

## 4.4. Тот же разбор в Apache

Около 30 мин. VirtualHost — это server. DocumentRoot — отдача файла. ProxyPass — та же стрелка, что proxy_pass.

**Теория**

Apache отвечает на те же пять вопросов другими словами. VirtualHost выбирает сайт по адресу, порту и ServerName. DocumentRoot — каталог файлов, аналог root. ProxyPass и ProxyPassReverse — передача запроса дальше и правка заголовков ответа, чтобы ссылки приложения не уехали мимо внешнего имени. Alias отдаёт отдельный URL из другого каталога: его легко не заметить и удивиться, откуда взялся файл.

Живой сайт на Ubuntu часто лежит не в apache2.conf, а в sites-enabled. Это ссылки на sites-available. Открытый файл в available ещё не значит, что он включён. apache2ctl -S печатает, какой VirtualHost на каком порту и имени победит. Это аналог собранного nginx -T для вопроса «кто вообще отвечает».

Чужой Apache читают тем же карандашом. Кто слушает. Какое ServerName. Какой путь в ProxyPass или в каталог. Куда пишет ErrorLog и CustomLog. Что будет, если процесс за ProxyPass молчит: снова ошибка шлюза, не «Apache исчез».

Учебный фрагмент:

```
<VirtualHost 127.0.0.1:8080>
  ServerName lab.local
  DocumentRoot /var/www/lab
  ProxyPass /api/ http://127.0.0.1:9000/
  ProxyPassReverse /api/ http://127.0.0.1:9000/
  ErrorLog /var/log/apache2/lab-error.log
  CustomLog /var/log/apache2/lab-access.log combined
</VirtualHost>
```

Рядом с nginx из прошлого урока это один рисунок. Снаружи порт и имя. Корень сайта — файлы. /api/ уходит на порт 9000. Журнал назван явно, его и открывают, когда ответ странный.

**Практика. Словарь на одном запросе**

Для запроса http://lab.local:8080/api/health выписать пару nginx и Apache: какой блок, куда уйдёт, какой журнал.

1. Таблица из двух колонок.
2. Блок сайта: server и VirtualHost.
3. Стрелка /api/.
4. Где журнал в фрагменте Apache и чего не хватает во фрагменте nginx.
5. Apache ставить не обязательно, если таблица честная. Если ставите — официальный пакет и только 127.0.0.1.

Сделано, когда:

- Таблица есть
- Стрелка /api/ совпала в обоих
- Наружу порт не открыт

### Проверка

**1. ProxyPass в Apache**

- А. та же передача запроса дальше, что proxy_pass ← верный ответ
- Б. каталог файлов
- В. проверка синтаксиса
- Г. имя журнала

Пояснение: Слова разные, стрелка одна.

## 4.5. Балансировщик

Около 30 мин. Балансировщик держит список целей и выбирает живую. Это не второй экземпляр вашего приложения.

**Теория**

Балансировщик стоит перед несколькими одинаковыми копиями сервиса. Клиент видит один адрес. Внутри список целей. nginx называет его upstream. Облачный балансировщик и Service в Kubernetes — тот же список: несколько целей и правило, кого выбрать. По кругу, по меньшему числу соединений или случайно. Для чтения чужой настройки важно не название алгоритма, а список целей и то, что происходит с мёртвой.

Если цель не принимает соединение, её на время вычеркивают. Иначе каждый второй запрос будет ошибкой. В nginx это параметры вроде max_fails у server внутри upstream. В облаке это проверка здоровья: какой путь дергать и какой ответ считать живым. Проверка на главную страницу, которая сама ходит в базу, может вычеркнуть здоровый процесс из-за чужой поломки. Это читают в конфиге проверки, не в алгоритме.

Липкая сессия нужна, когда приложение помнит пользователя в памяти одной копии. Тогда балансировщик старается вернуть клиента туда же. Если копия умерла, память сессии умерла вместе с ней. Балансировщик это не лечит. Лечит общая сессия или отсутствие состояния в памяти, о чём вы уже знаете по контейнерам.

Учебный upstream из двух целей, которые отвечают разным словом, показывает выбор. Обе цели — ваши контейнеры на localhost.

```
upstream lab {
  server 127.0.0.1:9001;
  server 127.0.0.1:9002;
}
server {
  listen 127.0.0.1:8080;
  location / { proxy_pass http://lab; }
}
```

> Цели upstream — только ваши процессы. Чужие адреса в список не добавляют.

**Практика. Два ответа с одного адреса**

Поставить две свои цели с разным текстом и увидеть оба текста через один порт 127.0.0.1.

1. Два простых ответа на 9001 и 9002, только localhost.
2. nginx с upstream на них и listen 127.0.0.1:8080.
3. Десять curl подряд, записать, какие тексты пришли.
4. Остановить одну цель и повторить.
5. Записать, остались ли ошибки и как часто.

Сделано, когда:

- Оба текста были
- После остановки одной цели картина понятна
- Чужих адресов в upstream нет

### Проверка

**1. Балансировщик**

- А. выбирает живую цель из списка ← верный ответ
- Б. хранит базу
- В. заменяет журнал
- Г. равен DocumentRoot

Пояснение: Снаружи один адрес, внутри список.

## 4.6. Чужой файл целиком

Около 35 мин. Сначала карта запроса, потом список того, что спросить у автора. Правку делают после проверки синтаксиса и только в своей копии.

**Теория**

Чужой конфиг на работе длинный, с копиями и комментариями, которые врут. Комментарий не исполняется. Исполняется директива. Поэтому карту строят по директивам, а комментарий отмечают отдельно: «автор думал так, строка делает иначе».

Порядок такой. Снять собранный конфиг, не править оригинал. Выписать каждый listen. Для одного конкретного URL, который «не работает», провести пять вопросов и записать цепочку. Открыть журнал этого сайта, не весь /var/log подряд. Сравнить с тем, что отвечает curl -sv на свой адрес. Только потом предлагать правку. Правку проверяют -t и смотрят на одном запросе. Перечитать файл после коллеги: include мог подключить вторую копию того же сайта.

Отдельные строки не чинят вслепую, но их замечают и спрашивают. Слушать все интерфейсы там, где хватило бы localhost. Каталог с автоиндексом, из которого браузер скачивает файлы. Location вроде /admin без ограничения, кто входит. proxy_pass на адрес, который не является вашим сервисом. default_server, который перехватывает чужие имена. Это вопросы автору и повод сузить, не инструкция, как такое спрятать.

Пока карта не сходится с ответом curl, конфиг не «почти понятен». Почти здесь и ломает вечер.

**Практика. Один чужой URL**

Разобрать придуманный или свой учебный файл так, будто его написал другой человек.

1. Взять собранный конфиг своего nginx или фрагменты этого модуля, склеенные в один файл.
2. Выбрать URL, который неочевиден, например /api/health.
3. Записать цепочку: listen, имя, location или ProxyPass, цель, журнал.
4. Отметить одну строку, которую вы бы спросили у автора, и почему.
5. Оригинал не менять, пока цепочка не записана. Если меняете учебную копию — сначала проверка синтаксиса.

Сделано, когда:

- Цепочка на один URL есть
- Вопрос автору сформулирован
- Боевая машина не правилась

### Проверка

**1. Комментарий в конфиге расходится со строкой под ним**

- А. верят строке и помечают комментарий как сомнительный ← верный ответ
- Б. верят комментарию
- В. файл недействителен
- Г. так выглядит балансировщик

Пояснение: Исполняется директива.

## Зачёт. Чужой конфиг веб-сервера

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. Пять вопросов**

- А. кто слушает, имя, путь, куда дальше, журнал ← верный ответ
- Б. только версия nginx
- В. только цвет страницы
- Г. размер диска

Пояснение: Так читают и nginx, и Apache.

**2. nginx -t**

- А. проверяет синтаксис ← верный ответ
- Б. доказывает верную схему
- В. открывает сайт наружу
- Г. заменяет журнал

Пояснение: Смысл читает человек.

**3. 502**

- А. прокси жив, цель молчит ← верный ответ
- Б. веб-сервер не стоит
- В. успех
- Г. ошибка имени в закладке всегда

Пояснение: Шлюз не дождался следующего процесса.

**4. ProxyPass**

- А. передача запроса дальше, как proxy_pass ← верный ответ
- Б. каталог файлов
- В. алгоритм баланса
- Г. проверка -t

Пояснение: Стрелка та же.

**5. Балансировщик**

- А. список целей и выбор живой ← верный ответ
- Б. копия базы
- В. журнал Apache
- Г. замена git

Пояснение: Один адрес снаружи.

**6. Чужой файл**

- А. сначала карта конкретного URL, потом правка ← верный ответ
- Б. сразу правка на сервере
- В. верят комментарию больше директивы
- Г. выключают журнал, чтобы не мешал

Пояснение: Карта сходится с ответом curl.

# 05. Kubernetes

Локальный кластер kind или minikube. Поды, выкладка, сервис, конфигурация и проверки живости. kubectl только к своему кластеру.

К концу модуля: Поднимаете учебное приложение в нескольких копиях и откатываете неудачную версию.

Уроков: 6. С зачётом около 3 ч 15 мин.

## 5.1. Кластер и зачем он нужен

Около 25 мин. Kubernetes держит желаемое число копий приложения и перезапускает упавшие.

**Теория**

После Docker одного контейнера на ноутбуке мало: в проде нужно несколько копий, смена версии без простоя и сеть между частями приложения. Kubernetes описывает желаемое состояние манифестами. Управляющий слой принимает эти манифесты, рабочие узлы запускают контейнеры. В 2026 году курс без Kubernetes не считают курсом DevOps: так устроены и Яндекс Практикум, и Нетология, и пути вроде KodeKloud. Для учёбы не нужен платный облачный кластер. kind поднимает узлы внутри Docker на вашем компьютере, minikube делает то же одной командой. kubectl указывает только на этот локальный контекст. Чужой кластер, найденный в интернете, не трогают.

> Не публикуйте API кластера в интернет и не подставляйте чужой kubeconfig.

**Практика. Свой маленький кластер**

Запустить kind или minikube и убедиться, что узел Ready.

1. Поставить kubectl и kind либо minikube с официальных страниц.
2. Создать кластер с именем вроде lab.
3. kubectl config current-context показывает ваш локальный контекст.
4. kubectl get nodes — узел Ready.
5. Чужих адресов в контексте нет.

Сделано, когда:

- Узел Ready
- Контекст локальный
- Облачный счёт не открыт

### Проверка

**1. Учебный Kubernetes**

- А. kind или minikube на своём компьютере ← верный ответ
- Б. чужой кластер из поиска
- В. обязательно платное облако
- Г. только Docker Compose

Пояснение: Идея та же, счёт не нужен.

## 5.2. Под

Около 25 мин. Под — минимальная единица запуска. Внутри один или несколько контейнеров с общей сетью.

**Теория**

Под живёт на узле, получает свой IP внутри кластера и умирает целиком, если его удалить. Контейнер в поде перезапускается по политике, но сам под не «чинится» заменой: для постоянного числа копий нужен контроллер из следующего урока. В учебном поде запускайте свой образ или официальный образ вроде nginx с фиксированным тегом, не latest. Процесс слушает порт. Корневой пользователь в контейнере не обязателен: в манифесте можно задать runAsNonRoot, когда образ это позволяет. Под без лимитов памяти на общем кластере может съесть узел; на учебном кластере лимиты всё равно стоит указать, чтобы привычка была.

**Практика. Один под**

Запустить под из манифеста и прочитать его логи.

1. Манифест Pod в git.
2. Образ с конкретным тегом.
3. kubectl apply и kubectl get pods.
4. kubectl logs показывает старт.
5. kubectl delete убирает под.

Сделано, когда:

- Под был Running
- Логи прочитаны
- Манифест в репозитории

### Проверка

**1. Удаление пода**

- А. убирает эту копию ← верный ответ
- Б. гарантирует, что она сама вернётся без контроллера
- В. удаляет образ с диска навсегда
- Г. равно helm uninstall

Пояснение: Без Deployment копию никто не поднимает заново.

## 5.3. Deployment и откат

Около 30 мин. Deployment держит число реплик и меняет версию по шагам.

**Теория**

Deployment создаёт ReplicaSet, а тот держит нужное число подов. Смена тега образа в манифесте запускает rolling update: новые поды поднимаются, старые уходят, когда новые готовы. Если новая версия падает, откат возвращает предыдущий ReplicaSet. Команда отката есть, но в GitOps источником правды останется git: иначе следующий sync вернёт сломанный манифест. Число реплик для учёбы — две. strategy.maxUnavailable не ставьте так, чтобы обе копии умерли сразу, пока вы не понимаете, зачем. kubectl edit на проде без коммита создаёт дрейф: через час никто не знает, что реально запущено.

**Практика. Две копии и откат**

Выложить Deployment, сменить тег на заведомо плохой и откатиться.

1. replicas: 2, образ с тегом.
2. Оба пода Ready.
3. Смена тега на несуществующий или падающий.
4. Увидеть проблему через rollout status или describe.
5. Откат и снова два Ready. В git вернуть рабочий тег.

Сделано, когда:

- Было две копии
- Плохая версия замечена
- Откат вернул рабочее

### Проверка

**1. Откат Deployment без правки git**

- А. кластер временно здоров, следующий sync из git может вернуть поломку ← верный ответ
- Б. навсегда чинит репозиторий
- В. удаляет образ
- Г. выключает сервис

Пояснение: Источник правды должен совпасть с кластером.

## 5.4. Service и Ingress

Около 25 мин. Service даёт стабильное имя подам. Ingress — вход снаружи, его не открывают всему интернету без нужды.

**Теория**

Поды приходят и уходят, их IP меняются. Service типа ClusterIP даёт имя внутри кластера и балансирует на готовые поды. NodePort открывает порт на узле: на ноутбуке это удобно для проверки, в интернет этот порт не пробрасывают. LoadBalancer в облаке заказывает внешний адрес и деньги; на kind его нет без дополнительной настройки. Ingress — правила HTTP к сервисам. Для учёбы хватает ClusterIP и kubectl port-forward к своему сервису. port-forward слушает ваш компьютер, не чужой. Не сканируйте сервисы чужих кластеров.

> NodePort и port-forward не публикуют в интернет.

**Практика. Имя вместо IP пода**

Поставить Service перед Deployment и открыть страницу через port-forward.

1. Service ClusterIP на порт приложения.
2. kubectl get endpoints показывает поды.
3. port-forward на localhost.
4. Страница открывается.
5. Правило проброса на роутере не создаёте.

Сделано, когда:

- Сервис видит поды
- Страница с localhost
- Наружу порт не торчит

### Проверка

**1. ClusterIP**

- А. имя внутри кластера ← верный ответ
- Б. белый адрес в интернет
- В. замена git
- Г. хранилище секретов

Пояснение: Снаружи его не видно.

## 5.5. ConfigMap и Secret

Около 25 мин. Настройки отдельно от образа. Секрет не коммитят и не печатают в лог.

**Теория**

Один образ ходит по средам, если адрес и флаги приходят снаружи. ConfigMap хранит несекретные настройки. Secret в кластере — для паролей и ключей, но манифест Secret в git в открытом виде равен утечке. В учебном репозитории секрет создают командой из локального файла, который в gitignore, либо подставляют на шаге, который не сохраняет значение. Приложение читает переменную окружения или файл, смонтированный в под. Смена ConfigMap не всегда перезапускает под сама: это частая причина «я поменял, а старое». После смены убедитесь, что под пересоздан. В логи значение секрета не пишут.

**Практика. Настройка без пересборки**

Вынести строку приветствия в ConfigMap и подключить к поду.

1. ConfigMap в git, без паролей.
2. Под читает её как env или файл.
3. Смена значения и перезапуск.
4. Страница или лог показывает новое.
5. Отдельный пароль, если нужен, только локально и в gitignore.

Сделано, когда:

- Образ не пересобирали
- Новое значение дошло
- Секрета в репозитории нет

### Проверка

**1. Пароль в манифесте Secret в git**

- А. это утечка ← верный ответ
- Б. так рекомендует Kubernetes
- В. gitignore его скроет задним числом
- Г. это ConfigMap

Пояснение: История git пароль сохранит.

## 5.6. Пробы и разбор падения

Около 25 мин. Readiness убирает под из сервиса, пока он не готов. Liveness перезапускает зависший процесс.

**Теория**

Без проб Service шлёт трафик в под, который ещё не слушает порт. Readiness probe говорит: в балансировку пока не брать. Liveness probe говорит: процесс завис, убей контейнер. Если liveness бьёт в тяжёлый запрос или срабатывает раньше, чем приложение стартовало, кластер будет перезапускать здоровый, но медленный старт по кругу. Для учёбы проба — простой HTTP на страницу здоровья или tcp на порт, с initialDelaySeconds больше времени старта. Когда под CrashLoopBackOff, смотрят describe и logs, а не удаляют под десять раз. Команды только к своему контексту.

**Практика. Под не готов, пока не слушает**

Добавить readiness и увидеть, что сервис ждёт готовый под.

1. Проба на порт приложения.
2. initialDelaySeconds с запасом.
3. kubectl describe показывает пробы.
4. Нарочно указать неверный порт и увидеть Not ready.
5. Вернуть верный порт.

Сделано, когда:

- Был Not ready
- Стал Ready
- Liveness не перезапускает старт по кругу

### Проверка

**1. Liveness на медленный старт без запаса**

- А. перезапускает ещё живой процесс ← верный ответ
- Б. ускоряет старт
- В. заменяет readiness
- Г. прячет логи

Пояснение: Запас по времени обязателен.

## Зачёт. Kubernetes

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. Учебный кластер**

- А. kind или minikube у себя ← верный ответ
- Б. любой открытый API
- В. только платный облачный
- Г. вместо Docker всегда

Пояснение: Контекст свой.

**2. Deployment**

- А. держит число копий и меняет версию ← верный ответ
- Б. равен одному поду без перезапуска
- В. хранит пароли
- Г. это реестр образов

Пояснение: ReplicaSet следит за числом.

**3. Откат только в кластере**

- А. git может вернуть поломку ← верный ответ
- Б. чинит репозиторий
- В. удаляет Service
- Г. не нужен

Пояснение: Манифест и кластер должны совпасть.

**4. ClusterIP**

- А. доступ внутри кластера ← верный ответ
- Б. белый IP
- В. проба живости
- Г. тег образа

Пояснение: Снаружи его нет.

**5. Секрет в git**

- А. утечка ← верный ответ
- Б. норма
- В. ConfigMap
- Г. проба

Пояснение: История помнит файл.

**6. Readiness**

- А. не пускает трафик, пока под не готов ← верный ответ
- Б. убивает медленный старт
- В. открывает NodePort в интернет
- Г. заменяет логи

Пояснение: Балансировка ждёт готовности.

# 06. Helm и GitOps

Пакет манифестов Helm и доставка через git. Argo CD подтягивает то, что лежит в репозитории. Откат — это коммит, не правка руками.

К концу модуля: Меняете тег образа в git и видите, как учебный кластер догоняет репозиторий.

Уроков: 6. С зачётом около 3 ч 5 мин.

## 6.1. Helm-чарт

Около 30 мин. Чарт — шаблон манифестов и файл значений. Один чарт, разные values для учебной и боевой среды.

**Теория**

Десяток yaml быстро расходится. Helm собирает их в чарт: шаблоны и values.yaml. Установка подставляет значения и применяет манифест. Для учёбы хватит своего чарта на Deployment и Service, без магазина чужих чартов с неясным содержимым. Чужой чарт читают до установки: какие права он просит и какие образы тянет. Пароль в values.yaml, который коммитят, — та же утечка, что пароль в манифесте. Секретные значения приходят из файла вне git или из секрет-хранилища, когда оно появится. Версию чарта поднимают, когда меняется шаблон, а не на каждый чих.

**Практика. Свой чарт**

Упаковать Deployment и Service в чарт и поставить его в локальный кластер.

1. helm create или минимальные Chart.yaml и templates.
2. Тег образа и число реплик в values.
3. Паролей в values нет.
4. helm template показывает yaml без сюрпризов.
5. helm upgrade --install в свой кластер.

Сделано, когда:

- Релиз стоит
- Шаблон в git
- Секретов в values нет

### Проверка

**1. Пароль в values.yaml в git**

- А. утечка ← верный ответ
- Б. так устроен Helm
- В. values всегда секретны и скрыты
- Г. это тег образа

Пояснение: Файл обычный, история его хранит.

## 6.2. Argo CD

Около 30 мин. GitOps: кластер сам приходит к состоянию из git. Человек не делает kubectl apply с ноутбука в прод.

**Теория**

Непрерывная доставка в 2026 году на курсах Яндекса и Нетологии всё чаще выглядит как Argo CD, а не как скрипт по SSH. Контроллер в кластере смотрит репозиторий и применяет изменения. Расхождение называется OutOfSync. Ручная правка kubectl создаёт такое расхождение, и следующий sync его затрёт. Учебный Argo ставят в тот же kind или minikube и указывают на свой репозиторий. Репозиторий форка незнакомца в автосинк не добавляют: чужой манифест применится с правами контроллера. Интерфейс Argo слушают локально, порт в интернет не открывают.

> Не подключайте к Argo чужой репозиторий с автосинком.

**Практика. Приложение из git**

Поставить Argo CD локально и завести одно приложение на свой репозиторий.

1. Официальная установка в свой кластер.
2. Пароль входа не коммитить.
3. Application указывает на ваш репозиторий и путь чарта или манифестов.
4. Статус Synced после первого применения.
5. Порт UI только на localhost.

Сделано, когда:

- Приложение Synced
- Источник — ваш git
- UI не торчит наружу

### Проверка

**1. kubectl edit при включённом автосинке**

- А. правка пропадёт, когда git применится снова ← верный ответ
- Б. становится новым источником правды
- В. отключает Argo
- Г. обновляет тег в реестре

Пояснение: Источник правды — коммит.

## 6.3. Тег образа в git

Около 20 мин. В values записывают неизменяемый тег. latest в GitOps не говорит, какая сборка запущена.

**Теория**

Пайплайн из модуля CI собрал образ с тегом коммита. Доставка — отдельный коммит, который меняет тег в values или в манифесте. Так видно, кто и когда сменил версию. Тег latest в репозитории не меняется, когда в реестре обновили слой, и Argo может ничего не заметить. Автоматический коммит тега из пайплайна допустим в учебный репозиторий, если он не обходит тесты. В прод такой робот пишет только после зелёного прогона и в ту ветку, которую вы разрешили. Откат — git revert этого коммита, затем sync.

**Практика. Смена версии коммитом**

Поменять тег в values, дождаться синка и увидеть новый под.

1. В values тег не latest.
2. Коммит и push.
3. Argo показывает новый коммит.
4. Под перешёл на этот тег.
5. Старый тег можно вернуть вторым коммитом.

Сделано, когда:

- Версия видна в git
- Под совпал с коммитом
- latest не используется

### Проверка

**1. latest в values при GitOps**

- А. не видно, какая сборка в кластере ← верный ответ
- Б. лучший выбор для отката
- В. равен хешу коммита
- Г. заменяет Argo

Пояснение: Файл не меняется, когда меняется слой.

## 6.4. Откат через git

Около 20 мин. Плохую версию убирают коммитом, который возвращает рабочий тег. Кластер догоняет.

**Теория**

Когда новая версия отвечает ошибкой, не начинайте с правки на сервере. Верните в git предыдущий тег. Argo применит его так же, как применял плохой. История останется: видно, что выкладывали и что отменили. Если автосинк выключен, нажмите sync сами после коммита. Пока под не Ready, смотрите события и логи, а не повторяйте sync в надежде, что само пройдёт. Если поломка в данных, а не в образе, откат образа её не лечит: это уже резервная копия, о которой вы знаете из курса администратора.

**Практика. Плохой тег и возврат**

Выложить заведомо плохой тег через git и вернуть рабочий тем же путём.

1. Коммит с плохим тегом.
2. Увидеть сбой пода.
3. Коммит возврата.
4. Sync и Ready.
5. Оба коммита есть в истории.

Сделано, когда:

- Сбой был виден
- Возврат через git
- Ручного edit в конце нет

### Проверка

**1. Откат GitOps**

- А. коммит с рабочим тегом и sync ← верный ответ
- Б. только перезагрузка ноутбука
- В. удаление git
- Г. тег latest

Пояснение: Кластер следует репозиторию.

## 6.5. Синий-зелёный и канарейка

Около 25 мин. Две стратегии смены версии. На учебном кластере достаточно понимать, когда какая нужна.

**Теория**

Скользящее обновление Deployment меняет поды по одному. Синий-зелёный держит две полные среды и переключает трафик целиком: откат быстрый, ресурсов нужно вдвое больше. Канарейка пускает новую версию на малую долю запросов и расширяет её, если ошибок нет. На курсах 2026 года эти слова ждут на собеседовании. В лаборатории не обязательно поднимать оба контура: нарисуйте, куда смотрит Service в каждом случае, и напишите, как выглядит откат. Канарейка не заменяет тесты в CI. Долю трафика не крутят на проде пользователей, которого у вас нет: учебный сервис — ваш.

**Практика. Схема на бумаге**

Для своего приложения выбрать одну стратегию и записать откат.

1. Что сейчас: rolling update.
2. Когда понадобился бы второй полный контур.
3. Как канарейка режет долю.
4. Как откатить каждый вариант.
5. Схему положить в заметку урока.

Сделано, когда:

- Три названия различены
- Откат описан
- Прод чужих людей не трогали

### Проверка

**1. Синий-зелёный**

- А. два полных контура и переключение трафика ← верный ответ
- Б. одна реплика без запаса
- В. сканирование чужой сети
- Г. хранение секретов в git

Пояснение: Откат — переключить обратно.

## 6.6. Дрейф и доверенный репозиторий

Около 20 мин. OutOfSync значит, что кластер и git разошлись. Автосинк включают только на свой репозиторий.

**Теория**

Дрейф появляется от ручных правок, от упавшего применения и от человека, который поменял объект в обход. Лечится не кнопкой «сделать git как кластер» наугад: сначала понимают, какая сторона правильная. Если правильный git, sync затирает ручную правку. Если в кластере срочный фикс, его несут в git тем же часом, иначе фикс исчезнет. Репозиторий, из которого Argo применяет манифесты, защищают так же, как main: чужой pull request не становится источником выкладки. Права Application в Argo не раздают всем подряд.

**Практика. Поймать дрейф**

Изменить число реплик вручную и увидеть OutOfSync, затем вернуть состояние из git.

1. Запомнить число реплик в git.
2. Поменять его kubectl scale.
3. Увидеть расхождение в Argo или сравнить манифест.
4. Sync из git.
5. Реплики снова как в коммите.

Сделано, когда:

- Дрейф замечен
- Git победил осознанно
- Чужой репозиторий не подключали

### Проверка

**1. Автосинк чужого репозитория**

- А. применит чужие манифесты с правами контроллера ← верный ответ
- Б. безопасен всегда
- В. только читает логи
- Г. равен helm template

Пояснение: Источник должен быть вашим.

## Зачёт. Helm и GitOps

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. Helm values с паролем в git**

- А. утечка ← верный ответ
- Б. норма чарта
- В. секрет прячется сам
- Г. это Chart.yaml

Пояснение: Обычный файл.

**2. Источник правды GitOps**

- А. git ← верный ответ
- Б. последний kubectl edit
- В. тег latest
- Г. память администратора

Пояснение: Кластер догоняет коммит.

**3. latest в GitOps**

- А. не показывает, какая сборка запущена ← верный ответ
- Б. лучше хеша
- В. нужен для отката
- Г. заменяет Argo

Пояснение: Файл не меняется.

**4. Откат**

- А. вернуть тег коммитом ← верный ответ
- Б. удалить кластер
- В. стереть git
- Г. открыть NodePort

Пояснение: Sync применит рабочее.

**5. Канарейка**

- А. малая доля трафика на новую версию ← верный ответ
- Б. два полных контура сразу
- В. выкладка без тестов
- Г. сканирование сети

Пояснение: Долю расширяют, если нет ошибок.

**6. OutOfSync**

- А. кластер и git разошлись ← верный ответ
- Б. всё хорошо
- В. реестр пуст
- Г. проба живости

Пояснение: Сначала решают, какая сторона верная.

# 07. Инфраструктура как код

Terraform или OpenTofu и Ansible. План до применения, состояние не в git. Лаборатория на локальном провайдере, без счёта облака.

К концу модуля: Описываете ресурс в файле, смотрите план и применяете его к своей машине.

Уроков: 6. С зачётом около 3 ч 10 мин.

## 7.1. Почему не клики

Около 20 мин. Сервер, собранный мышкой, нельзя повторить и нельзя отревьюить.

**Теория**

Инфраструктура как код — те же коммиты, что у приложения: видно, кто добавил диск или пользователя, и можно обсудить изменение до применения. Terraform и открытый OpenTofu описывают желаемые ресурсы. Ansible описывает шаги настройки машины. Облака в программах Нетологии и Практикума — Яндекс Облако или AWS. Форма та же: провайдер, ресурс, план, применение. Чтобы не платить за время учёбы, провайдер в лаборатории локальный: docker или local_file. Когда тот же файл позже укажет на облако, вы уже умеете читать план. Чужой аккаунт и чужой проект не трогают.

**Практика. Что кодируем**

Выписать три вещи, которые в офисе обычно кликают, и решить, код это или разовая операция.

1. Например пользователь, пакет, контейнер.
2. Что опасно сделать дважды вручную.
3. Что должно переживать переустановку.
4. Список в заметке.
5. Облачный аккаунт не заводить.

Сделано, когда:

- Список из трёх пунктов
- Понятно, зачем файл
- Счёта нет

### Проверка

**1. Инфраструктура в файле**

- А. изменение можно прочитать до применения ← верный ответ
- Б. заменяет резервные копии
- В. нужна только в облаке
- Г. прячет пароли сама

Пояснение: Ревью происходит до apply.

## 7.2. План и применение

Около 35 мин. plan показывает, что изменится. apply делают после чтения плана.

**Теория**

Команда plan сравнивает файлы с состоянием и печатает, что будет создано, изменено или удалено. Строка destroy в учебном плане — повод остановиться. apply без плана вслепую на живой среде так и ломает лишние ресурсы. В лаборатории поставьте OpenTofu или Terraform и провайдер, который не ходит в платное API: создайте локальный файл или контейнер с фиксированным образом. Каталог .terraform и бинарники провайдера в git не кладут, для этого есть .gitignore. Версию провайдера фиксируют, чтобы завтра план не поехал из-за чужого обновления.

**Практика. Сначала план**

Описать один локальный ресурс, прочитать plan и только потом apply.

1. Установить OpenTofu или Terraform с официального сайта.
2. Ресурс без облака.
3. plan без неожиданного destroy.
4. apply.
5. Повторный plan пустой.

Сделано, когда:

- План прочитан
- Ресурс появился
- Второй план пустой

### Проверка

**1. destroy в плане**

- А. остановиться и понять, что удалится ← верный ответ
- Б. сразу apply
- В. это всегда безопасно
- Г. значит, план пустой

Пояснение: Удаление читают до применения.

## 7.3. Файл состояния

Около 25 мин. State помнит, какие реальные объекты соответствуют коду. В нём бывают секреты. В git его не кладут.

**Теория**

Состояние связывает ресурс в файле с объектом в мире. Потеряли файл — инструмент думает, что мира нет, и захочет создать всё заново или запутается. На одном ноутбуке файл живёт локально и в бэкапе, который не является репозиторием. В команде состояние держат в удалённом хранилище с блокировкой, чтобы двое не сделали apply одновременно. Пароли, которые провайдер вернул, часто лежат в state в открытом виде. Поэтому state не коммитят, не кидают в чат и не кладут в публичный бакет. Если файл уже утёк, секрет меняют, а не надеются, что следующий коммит сотрёт историю.

> Не коммитьте terraform.tfstate и не выкладывайте его в общий чат.

**Практика. Состояние вне git**

Убедиться, что state в .gitignore и не попал в коммит.

1. Найти файл состояния после apply.
2. Добавить его в gitignore.
3. git status не показывает state.
4. В репозитории нет копии.
5. Понять, где лежит единственная копия и как вы её не потеряете на своём диске.

Сделано, когда:

- State не в git
- Место копирования понятно
- Секретов в коммите нет

### Проверка

**1. terraform.tfstate в git**

- А. риск секретов и гонок ← верный ответ
- Б. так рекомендуют
- В. заменяет план
- Г. нужен для .gitignore наоборот

Пояснение: Состояние не является исходником.

## 7.4. Дрейф

Около 20 мин. Кто-то поменял ресурс руками. Следующий план это покажет.

**Теория**

Дрейф — расхождение мира и кода, то же, что OutOfSync у Argo. plan после ручной правки предлагает вернуть описанное. Прежде чем согласиться, спросите, не был ли ручной шаг срочным ремонтом. Импорт существующего объекта в state делают, когда объект уже есть и вы берёте его под код. Импортировать чужой боевой проект «чтобы посмотреть» нельзя: apply следом может его изменить. На лаборатории измените свой локальный ресурс вне инструмента и посмотрите, что скажет plan. Затем решите: поправить код под факт или вернуть факт под код.

**Практика. Поймать расхождение**

Изменить свой ресурс в обход кода и прочитать plan.

1. Запомнить, что в файле.
2. Поменять объект руками.
3. plan показывает разницу.
4. Выбрать сторону и применить осознанно.
5. Повторный план пустой.

Сделано, когда:

- Разница была видна
- Решение записано
- Чужой проект не импортировали

### Проверка

**1. Импорт чужого боевого ресурса ради учёбы**

- А. нельзя: apply может его изменить ← верный ответ
- Б. обычное упражнение
- В. только читает
- Г. заменяет бэкап

Пояснение: Под код берут своё.

## 7.5. Ansible на свою машину

Около 30 мин. Плейбук ставит пакет и кладёт файл. Запускают на localhost или на свою виртуальную машину.

**Теория**

Ansible подключается по SSH или к localhost и приводит машину к описанию в плейбуке. Идемпотентность значит: второй запуск не ломает то, что уже сделано. Модули пакетов и файлов лучше свободной shell-команды, потому что видно намерение. become повышает привилегии; на учебной ВМ это нормально, на чужой машине — нет. inventory с боевыми адресами не коммитят, если это секрет компании; для учёбы там localhost. Пароли в открытом inventory не хранят. Проверять плейбук на проде офиса, где вы не администратор, нельзя.

**Практика. Плейбук дважды**

Поставить пакет или создать файл плейбуком и запустить его второй раз без сюрприза.

1. inventory: localhost.
2. Один модуль с понятным итогом.
3. Первый запуск меняет систему.
4. Второй почти ничего не меняет.
5. Секретов в плейбуке нет.

Сделано, когда:

- Эффект есть
- Второй запуск спокоен
- Цель — своя машина

### Проверка

**1. Второй запуск хорошего плейбука**

- А. не портит уже сделанное ← верный ответ
- Б. всегда сносит систему
- В. нужен только один раз в жизни и файл удаляют
- Г. кладёт пароль в git

Пояснение: Идемпотентность — смысл описания.

## 7.6. Тот же план в облаке

Около 20 мин. Яндекс Облако и AWS в вакансиях — другой провайдер и те же plan и apply. Счёт для этого курса не обязателен.

**Теория**

Когда в дипломе Нетологии делают облако, студент заводит проект, смотрит план и применяет сеть и виртуалку. Ошибки те же: забыть удалить ресурс и платить, открыть порт в интернет, положить ключ в репозиторий. Вы уже видели план и state локально. Облачный провайдер добавляет учётную запись, биллинг и сеть. Учебный ключ облака, если когда-нибудь появится, живёт вне git и с минимальными правами. Этот курс сознательно останавливается до счёта: форма инструмента уже ваша. В резюме честно пишут «локальный провайдер и плейбук», а не «прод в AWS», если AWS не было.

**Практика. Словарь облака**

Сопоставить локальный ресурс с тем, чем он был бы в облаке, без регистрации.

1. Файл или контейнер у вас.
2. Как назывался бы аналог виртуалки и диска.
3. Где в облаке прятали бы state.
4. Какой порт вы не открыли бы в интернет.
5. Аккаунт не создавать.

Сделано, когда:

- Аналогия записана
- Риск порта назван
- Ключей облака нет

### Проверка

**1. Ключ облака в репозитории**

- А. меняют и убирают из истории, не оставляют ← верный ответ
- Б. так и задумано провайдером
- В. gitignore лечит старый коммит
- Г. это state и его можно публиковать

Пояснение: Утёкший ключ считают скомпрометированным.

## Зачёт. Инфраструктура как код

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. plan**

- А. показывает изменения до apply ← верный ответ
- Б. сразу меняет мир
- В. хранит секреты в git
- Г. равен Ansible

Пояснение: Сначала читают.

**2. destroy в плане**

- А. повод остановиться ← верный ответ
- Б. всегда применяют
- В. пустой план
- Г. проба Kubernetes

Пояснение: Удаление проверяют.

**3. state в git**

- А. риск секретов ← верный ответ
- Б. рекомендация
- В. замена плана
- Г. плейбук

Пояснение: Состояние не коммитят.

**4. Дрейф**

- А. мир и код разошлись ← верный ответ
- Б. план пустой всегда
- В. так называют Helm
- Г. это тег latest

Пояснение: plan покажет разницу.

**5. Ansible второй раз**

- А. не должен портить результат ← верный ответ
- Б. сносит машину
- В. только для облака
- Г. кладёт state в git

Пояснение: Плейбук идемпотентен.

**6. Чужой боевой проект в учебный state**

- А. не импортируют ← верный ответ
- Б. обычная лаба
- В. безопасное чтение

Пояснение: apply может изменить чужое.

# 08. Наблюдаемость

Метрики Prometheus, графики Grafana и осмысленные оповещения. Логи без секретов. Zabbix остаётся в офисах, основной инструмент курса — Prometheus.

К концу модуля: Видите, живо ли учебное приложение, и знаете, какое оповещение требует человека.

Уроков: 6. С зачётом около 3 ч.

## 8.1. Метрики, логи, следы

Около 20 мин. Метрика отвечает «сколько». Лог отвечает «что случилось». След отвечает «куда шёл запрос».

**Теория**

Выкладка без наблюдения — это сюрприз ночью. Метрики — числа во времени: запросы, ошибки, занятая память. Логи — строки событий. Следы связывают один запрос через несколько сервисов; на первом приложении они не обязательны, слово стоит знать. Курс учит Prometheus и Grafana, потому что так устроены современные программы DevOps. В российском офисе рядом часто стоит Zabbix: агент, триггер, дашборд. Идея оповещения та же. Собирать метрики чужих сайтов в интернете не нужно и нельзя. Цель — свой под, свой контейнер или свой localhost.

**Практика. Три вопроса к своему сервису**

Записать, какую метрику, какой лог и какой сигнал «пора смотреть» вы хотите.

1. Жив ли процесс.
2. Растёт ли число ошибок.
3. Куда писать лог: stdout, как в уроке Docker.
4. Что не является секретом в логе.
5. Чужие адреса в список не входят.

Сделано, когда:

- Три пункта есть
- Секреты исключены
- Цель своя

### Проверка

**1. Метрика**

- А. число во времени ← верный ответ
- Б. замена резервной копии
- В. пароль в дашборде
- Г. сканирование сети

Пояснение: График строится из чисел.

## 8.2. Prometheus на своём контуре

Около 30 мин. Prometheus забирает метрики с целей, которые вы указали. Цели — ваши.

**Теория**

Prometheus по расписанию опрашивает HTTP-адреса /metrics. Конфигурация — файл с целями. В лаборатории цель может быть сам Prometheus и, если есть, экспортёр узла на вашей машине или метрики учебного приложения. В конфиг не пишут чужие домены. Хранилище на ноутбуке маленькое: срок хранения укорачивают, чтобы диск не кончился. Выражение PromQL для учёбы простое: жива ли цель и сколько памяти. Ошибку выражения видно в интерфейсе, его не тыкают в прод компании. Порт интерфейса слушает localhost.

> Не добавляйте в scrape чужие адреса из интернета.

**Практика. Одна цель**

Запустить Prometheus в Docker и увидеть, что он сам себе цель и она up.

1. Официальный образ с фиксированным тегом.
2. Конфиг только со своей целью.
3. Интерфейс на localhost.
4. Запрос up равен 1.
5. Конфиг без секретов и без чужих хостов.

Сделано, когда:

- up равен 1
- Порт не проброшен на роутере
- Тег образа конкретный

### Проверка

**1. Цели Prometheus**

- А. только свои сервисы ← верный ответ
- Б. любые сайты для практики
- В. замена kubectl
- Г. файл state Terraform

Пояснение: Опрос чужого адреса вам не принадлежит.

## 8.3. График в Grafana

Около 25 мин. Один график лучше десяти. Источник — ваш Prometheus.

**Теория**

Grafana рисует запросы к Prometheus. Для учёбы хватит одного дашборда: цель жива, занято место или память. Дашборд можно описать файлом и положить в git, без паролей источника. Пароль администратора Grafana не admin/admin на машине, до которой кто-то может достучаться, и не в репозитории. Анонимный доступ наружу не включают. Красивый дашборд чужой компании импортировать «как есть» с неизвестными плагинами не стоит: плагин — это код. Официальный образ и свой простой график учат больше.

**Практика. Один график up**

Подключить Grafana к своему Prometheus и показать up.

1. Grafana на localhost, пароль не в git.
2. Источник данных — ваш Prometheus.
3. Панель с up.
4. Дашборд сохранён.
5. Анонимный доступ в интернет выключен.

Сделано, когда:

- График есть
- Пароль не в репозитории
- Источник свой

### Проверка

**1. Пароль Grafana в git**

- А. утечка ← верный ответ
- Б. так шарят дашборды
- В. нужен для PromQL
- Г. это метрика

Пояснение: В git кладут описание панели, не пароль.

## 8.4. Оповещение, на которое можно ответить

Около 25 мин. Тревога, которая горит всегда, её перестают читать. У каждой тревоги есть действие.

**Теория**

Правило смотрит выражение и держит его истинным несколько минут, чтобы одиночный всплеск не будил человека. Текст тревоги говорит, что сломалось и куда смотреть: график, лог, имя сервиса. «CPU высокий» без порога и без действия бесполезно. На учебной машине получатель — вы, в файл или в интерфейс, не SMS незнакомым людям. Ночью будят из-за недоступности сервиса, а не из-за каждого предупреждения. Когда тревога ложная, правят правило, а не отключают всё наблюдение. Секреты в подпись тревоги не подставляют.

**Практика. Правило на up**

Сделать тревогу, когда ваша цель пропадает, и один раз увидеть её срабатывание.

1. Выражение up == 0.
2. Короткая задержка, чтобы успеть заметить в лаборатории.
3. Остановить цель.
4. Увидеть тревогу.
5. Вернуть цель и записать, какое действие вы бы сделали.

Сделано, когда:

- Тревога сработала
- После старта погасла
- Действие записано

### Проверка

**1. Тревога без действия**

- А. её перестанут читать ← верный ответ
- Б. чем больше, тем лучше
- В. заменяет логи
- Г. нужна для Helm

Пояснение: Человек должен знать, что делать.

## 8.5. Логи без секретов

Около 20 мин. Приложение пишет в stdout. В строке нет пароля, токена и персонального хвоста, который вам не нужен.

**Теория**

Контейнер уже пишет лог в stdout, его забирает среда. На одном компьютере хватает docker logs или kubectl logs. Сбор в отдельное хранилище нужен, когда узлов много и контейнер умер вместе с диском. Учебный стек вроде связки сбора логов ставить не обязательно, если вы честно прочитали свои строки и выкинули из них секрет. Постоянный DEBUG на проде забивает диск и может напечатать заголовок авторизации. Срок хранения логов согласуют: бесконечный ящик с персональными данными — отдельная ответственность, не «на всякий случай». Чужие логи читать негде: только свои контейнеры.

**Практика. Чистая строка**

Найти в своём приложении место, где в лог мог бы попасть секрет, и убрать его.

1. Открыть лог своего контейнера или пода.
2. Найти шумную или опасную строку.
3. Убрать значение, оставить факт события.
4. Перезапустить и проверить.
5. Срок «зачем мы это храним» записать одной фразой.

Сделано, когда:

- Секрета в логе нет
- Событие всё ещё понятно
- Чужие системы не смотрели

### Проверка

**1. Токен в строке лога**

- А. считают утёкшим ← верный ответ
- Б. удобно для отладки прода
- В. Grafana его скроет
- Г. это метрика

Пояснение: Логи читают люди и системы.

## 8.6. Zabbix в офисе

Около 20 мин. Во многих компаниях мониторинг уже Zabbix. Вы узнаете в нём те же цели, триггеры и графики.

**Теория**

Zabbix ставит агент на сервер, собирает пункты данных и зажигает триггер. Это близко к цели Prometheus и правилу оповещения. Отличие в модели и в том, что офисный Zabbix часто уже настроен годами. Приходя на работу, не сносят его в первую неделю ради модного стека. Сначала понимают, какие триггеры будят людей и какие врут. Новый сервис можно отдать в существующую систему. В лаборатории Zabbix не обязателен, если Prometheus уже показывает up: на собеседовании вы говорите, как называется аналог. Агент ставят на свою ВМ, не на чужой сервер.

**Практика. Словарь**

Сопоставить up, график и тревогу Prometheus со словами Zabbix.

1. Цель — узел или агент.
2. Выражение — элемент данных.
3. Тревога — триггер.
4. Grafana — панель или экран.
5. Zabbix ставить не обязательно.

Сделано, когда:

- Четыре пары записаны
- Свой Prometheus ещё жив
- Чужой сервер не трогали

### Проверка

**1. Zabbix на новой работе**

- А. сначала понять действующие триггеры ← верный ответ
- Б. сразу удалить и поставить только Prometheus
- В. это система контроля версий
- Г. замена Terraform

Пояснение: Людей уже будит какая-то система.

## Зачёт. Наблюдаемость

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. Метрика**

- А. число во времени ← верный ответ
- Б. пароль
- В. манифест
- Г. плейбук

Пояснение: График из чисел.

**2. Цели scrape**

- А. свои сервисы ← верный ответ
- Б. интернет для практики
- В. чужой кластер
- Г. state файл

Пояснение: Опрашивают своё.

**3. Пароль Grafana в git**

- А. утечка ← верный ответ
- Б. норма дашборда
- В. PromQL
- Г. триггер

Пояснение: В git описание панели.

**4. Тревога без действия**

- А. шум ← верный ответ
- Б. чем больше тем лучше
- В. замена бэкапа
- Г. GitOps

Пояснение: Нужен следующий шаг человека.

**5. Секрет в логе**

- А. утёк ← верный ответ
- Б. так отлаживают прод
- В. метрика
- Г. values.yaml так и надо

Пояснение: Строку читают.

**6. Zabbix и Prometheus**

- А. разные инструменты одной задачи наблюдения ← верный ответ
- Б. Zabbix заменяет git
- В. Prometheus нельзя графить
- Г. триггер равен Helm

Пояснение: Цель, число, тревога.

# 09. Поставка и доступ

Свой образ, проверка известным сканером, секреты вне git, узкие права в кластере и сеть между подами. В конце собираете весь путь от коммита до отката.

К концу модуля: Учебный путь закрыт: код, проверка, образ с тегом, кластер, наблюдение и откат.

## 9.1. Откуда взялся образ

Около 25 мин. Базовый образ официальный и с версией. Случайный образ с общим числом скачиваний — не аргумент.

**Теория**

Цепочка поставки — это всё, что попадает в сборку: базовый образ, пакеты, действия GitHub с чужого репозитория. Закрепляют версию. Действие в пайплайне указывают на конкретный коммит, когда учитесь серьёзнее, а не на плавающую ветку. Официальный образ с страницы проекта предпочтительнее пересборки неизвестного автора. В Dockerfile не отключают проверку сертификатов ради скорости. Секрет, попавший в слой, остаётся в истории образа, даже если следующий слой файл удалил. Такой образ пересобирают без секрета и считают старый тег скомпрометированным.

**Практика. Список оснований**

Для своего Dockerfile записать базовый образ, тег и откуда он.

1. Имя и тег, не latest.
2. Официальный источник.
3. Нет секрета в RUN и COPY.
4. Действия пайплайна со своего или известного репозитория.
5. Чужой кластер не используется.

Сделано, когда:

- Образ назван точно
- Секрета в слоях нет
- Источник понятен

### Проверка

**1. Секрет в слое образа**

- А. остаётся в истории образа ← верный ответ
- Б. исчезает, если следующий слой удалил файл
- В. gitignore чинит реестр
- Г. это ConfigMap

Пояснение: Слой уже опубликован.

## 9.2. Проверка своего образа

Около 25 мин. Сканер ищет известные проблемы в вашем образе. Чужие сети и чужие кластеры не проверяют.

**Теория**

Trivy и похожие сканеры читают образ, который вы собрали, и сверяют пакеты со списками известных уязвимостей. Это не «взлом» и не поиск дыр в чужой компании. В лаборатории прогоните сканер по своему тегу. Критичные находки в базовом образе лечат обновлением тега базы и пересборкой, а не отключением проверки. Ложный шум тоже бывает: его записывают, почему проигнорировали, а не ставят игнор на всё. Сканер в пайплайне ставит после сборки и до выкладки. Отчёт не должен печатать секреты, их в образе и так быть не должно.

> Сканируйте только образы и файлы, которые собираете вы.

**Практика. Отчёт по своему тегу**

Запустить официальный сканер против своего образа и решить, что делать с верхней находкой.

1. Образ уже собран вами.
2. Команда сканера по этому имени.
3. Прочитать хотя бы одну строку отчёта.
4. Либо обновить базу, либо записать, почему строка не блокирует учёбу.
5. В конфиг не добавлять чужие адреса.

Сделано, когда:

- Отчёт есть
- Решение по одной находке записано
- Цель — свой образ

### Проверка

**1. Сканер в курсе**

- А. смотрит ваш образ до выкладки ← верный ответ
- Б. ищет открытые порты в интернете
- В. заменяет тесты
- Г. кладёт пароль в отчёт специально

Пояснение: Это проверка поставки, не чужой сети.

## 9.3. Секрет вне репозитория

Около 25 мин. Пароль живёт в менеджере секретов или в файле вне git. Утечку в истории не лечит новый коммит.

**Теория**

Места, которые вы уже видели: .env, values, манифест, state, лог, слой образа, переменная CI. Правило одно. В репозитории лежит пример без значений. Настоящее значение подставляется в среде. Если секрет всё же запушили, его меняют у источника, потому что копия осталась в истории и, возможно, в форках. Чистить историю имеет смысл только после смены значения. В CI секрет маскируют и не печатают. В кластере его монтируют в под, а не запекают в образ. Права на секрет в облаке, если оно появится, дают сервису, а не всем разработчикам.

**Практика. Проверка перед коммитом**

Просмотреть diff и убедиться, что в нём нет значений секретов.

1. git status и diff.
2. Нет .env, state, kubeconfig с ключами.
3. Пример файла без значений можно коммитить.
4. Если что-то секретное уже было в истории, значение сменить, не только удалить файл.
5. Запушить только чистый diff.

Сделано, когда:

- Diff чистый
- Пример без значений есть
- Старые утечки не оставлены «как есть»

### Проверка

**1. Секрет удалили новым коммитом**

- А. в истории он ещё есть, значение меняют ← верный ответ
- Б. проблема закрыта
- В. gitignore стирает прошлое
- Г. Argo его шифрует сам

Пояснение: Сначала ротация, потом история.

## 9.4. Права в кластере

Около 25 мин. Приложению не нужна роль администратора кластера. Человеку для учёбы хватает своего контекста.

**Теория**

RBAC решает, кто может читать и менять объекты. Учётка пода — ServiceAccount. Привязка cluster-admin к приложению означает, что ошибка в приложении равна полным правам на кластер. Учебному поду хватает прав по умолчанию, без дополнительной широкой роли. Свой пользователь в kubeconfig — администратор учебного кластера на ноутбуке, и этот файл не коммитят: в нём ключ. На работе права просят узкие: namespace и глаголы, которые нужны для выкладки. Проверять чужие права и обходить отказ нельзя. Если манифест чарта просит cluster-admin, вы спрашиваете зачем, а не применяете молча.

**Практика. Кто такой под**

Посмотреть ServiceAccount своего пода и убедиться, что вы не выдавали ему cluster-admin.

1. kubectl описывает под в своём namespace.
2. Имя учётной записи пода.
3. В манифестах нет привязки к cluster-admin.
4. kubeconfig не в git.
5. Контекст по-прежнему локальный.

Сделано, когда:

- Учётка узкая
- Ключ не в репозитории
- Чужой кластер не подключали

### Проверка

**1. cluster-admin у приложения**

- А. слишком широко ← верный ответ
- Б. рекомендация для каждого пода
- В. нужно для ConfigMap
- Г. заменяет пробы

Пояснение: Поду дают только нужные глаголы.

## 9.5. Кто с кем говорит

Около 20 мин. Сетевая политика описывает, каким подам можно ходить друг к другу. Это правило кластера, не инструкция обхода.

**Теория**

По умолчанию во многих установках под может открыть соединение к любому другому поду. Политика сужает это: база принимает вход только от приложения, приложение принимает вход только от ingress. На учебном кластере политику пишут, когда понимают метки подов. Если после применения пропала связь, смотрят, какая метка не совпала, и чинят правило, а не отключают сеть всего узла. Политика не заменяет файрвол офиса и не публикует сервисы наружу. Обходить чужую политику, чтобы «проверить», не входят в курс. Достаточно одной разрешающей схемы для своих двух подов и проверки, что без метки связи нет.

**Практика. База только от приложения**

Нарисовать или применить правило: учебная база принимает вход только от пода приложения.

1. Две метки: app и db.
2. Правило на свой namespace.
3. Приложение доходит.
4. Под без метки не доходит, если политика уже действует в вашей установке.
5. Если плагин политики в кластере не включён, схема на бумаге и явная пометка, что в этом kind правила ещё не принудительны.

Сделано, когда:

- Схема есть
- Разрешён только свой трафик
- Чужие сети не сканировали

### Проверка

**1. Сетевая политика**

- А. сужает, кто ходит к поду ← верный ответ
- Б. открывает API кластера в интернет
- В. хранит секреты
- Г. заменяет CI

Пояснение: Это список разрешённых входов.

## 9.6. Сквозной путь

Около 35 мин. От ветки до отката: один учебный сервис проходит все ступени, которые вы уже сделали.

**Теория**

Итоговая работа не новый инструмент, а связь старых. Ветка и пул-реквест. Пайплайн гоняет тест и собирает образ с тегом коммита. Секретов в diff нет. Образ ваш, тег не latest. Манифест или values в git. Кластер локальный догоняет git. График или хотя бы лог показывает, что сервис жив. Плохой тег возвращают коммитом. Этот набор совпадает с тем, что публичные программы 2026 года раскладывают на месяцы: Git, CI, Docker, Kubernetes, GitOps, инфраструктура как код и наблюдение. Облачный счёт по-прежнему не нужен. В резюме так и пишут: учебный контур на своём компьютере, без выдуманного прода.

**Практика. Один сервис, все ступени**

Пройти чеклист на уже собранном приложении и отметить, какого звена не хватает.

1. Коммит в вашей ветке, main защищён тестом.
2. Образ с тегом коммита.
3. Выкладка из git в свой кластер.
4. Лог или метрика без секрета.
5. Откат коммитом проверен хотя бы один раз за курс.
6. Недостающее звено доделать, а не отметить галочкой.

Сделано, когда:

- Чеклист честный
- Откат был
- Наружу ничего не опубликовано

### Проверка

**1. Итог курса**

- А. свой путь от коммита до отката на локальном контуре ← верный ответ
- Б. платный прод в интернете
- В. права администратора на чужой кластер
- Г. секрет в git для скорости

Пояснение: Связность важнее нового инструмента.

## Зачёт. Поставка и доступ

Около 40 мин. Нужно примерно три четверти верных ответов.

**1. Секрет в слое**

- А. остаётся в истории образа ← верный ответ
- Б. стирается следующим слоем
- В. лечится latest
- Г. это проба

Пояснение: Образ пересобирают, секрет меняют.

**2. Сканер курса**

- А. ваш образ ← верный ответ
- Б. чужая сеть
- В. замена отката
- Г. state в git

Пояснение: Проверяют поставку.

**3. Удаление секрета новым коммитом**

- А. значение всё равно меняют ← верный ответ
- Б. достаточно
- В. gitignore стирает историю
- Г. Argo шифрует прошлое

Пояснение: История помнит.

**4. cluster-admin у пода**

- А. слишком широкие права ← верный ответ
- Б. норма
- В. нужно для логов
- Г. равно Service ClusterIP

Пояснение: Права узкие.

**5. Сетевая политика**

- А. кто может подключиться к поду ← верный ответ
- Б. публикация API
- В. сканер портов
- Г. файл состояния

Пояснение: Список разрешённых связей.

**6. Откат в итоге**

- А. коммит с рабочим тегом ← верный ответ
- Б. правка только на сервере
- В. тег latest
- Г. выключение мониторинга

Пояснение: Git остаётся источником.
